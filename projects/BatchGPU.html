OVERVIEW

BatchGPU is an exchange for GPU compute that clears in hourly batches inspired by Diamandis, Chitra and Angeris, “Market Clearing with Semi-fungible Assets” (2025). Buyers and sellers send orders for node-hours (one node, an indivisible unit of compute, for one hour); once an hour the exchange clears everything it holds together and gives every item that traded (one kind of node in one hour) one price. It is a portfolio project: it clears and records, and does not settle, deliver or take payment.

A bid lists the models, interconnects (PCIe or NVLink), regions, and hours it would accept. For example, a buyer can specify indifference to an A100 or an H100 and can be served by either.

Batches suit flexible bids: separate order books per model, region and hour would split a thin market into many thinner ones, and at an hourly period nobody races for the front of a queue. This is a call auction (orders gathered, then cleared together) with substitution.

Networking, replication and failover come from ToyExchange Core, which EventContractLOB also runs on. Core's gateway takes in clients' commands, numbers each into one sequenced log and multicasts it to replicas that each run the engine of the exchange built on Core (a “product”), so all of them must reach the same result from the same log. BatchGPU is such a product: it supplies the engine, a clearing module, a batch clock, a recorder and a read-only results API.

WHAT IS TRADED

An item is one SKU in one hourly delivery slot, such as 13:00–14:00. A SKU is a model, an interconnect and a region: five models, two interconnects and three regions make 30 SKUs, and a batch sells the 47 hourly slots that follow its clear, so 1,410 items are on offer. A price is a whole number of ticks of $0.01 per node-hour. The catalog, the fixed list of models, interconnects and regions are part of the protocol: every replica must run the same one.

  • Models are ranked within a vendor (A100 < H100 < H200 for NVIDIA); MI300X (AMD) and TPU-v5p (Google) stand alone. Interconnects are ranked too, PCIe < NVLink. Regions are uncomparable. Together these rankings are a partial order: some SKUs compare, others do not.
  • A SKU is strictly better than another when it has the same region and vendor, is no lower on interconnect or model, and is not the same SKU. A unit is lifted when it is awarded a SKU strictly better than one the order accepts. Fills and the clear's statistics report lifted units.

  • Curve. Up to four steps of (quantity, price). A bid's prices never rise from step to step and an ask's never fall, which keeps the problem convex: the best step fills first, and each step can be its own arc.
  • Per-slot cap. It limits the nodes an order may take or offer in any one hour, so “10 node-hours in a 10-hour window” cannot fill as 10 nodes in one hour. It goes beyond the paper's model; in the flow it is an arc capacity.

CLEARING A BATCH

The exchange clears once an hour, at half past (UTC). BATCH_CLEAR is a command like any other, sent by a ticker (a timer) in the gateway's process, so it is sequenced and replicated with everything else and every replica meets it at the same place in the log. No replica reads its own clock to decide anything; the engine derives each clear's time from the batch id.

A batch is not a clock hour. It is the orders that arrive between two clears, half past to half past (the open batch is the one taking orders now), and it sells the 47 hourly slots from the first hour mark after its clear. A 12:30 clear sells from 13:00, so the lead, the time from clear to first slot, is always 30 minutes. An order is placed against two clocks:

  • When it arrives decides its batch. Sent at 12:10 it clears at 12:30; sent at 12:40, at 13:30.
  • Which hours it names must all be on sale to that batch. At 12:10 the open batch sells from 13:00, so naming the 12:00–13:00 slot is rejected with SLOT_NOT_ELIGIBLE: the last batch that could sell it cleared at 11:30.

The engine keeps no clock, so a late or missing clear leaves the open batch on its old window until the next clear arrives. An order that does not fill lapses at the clear; nothing carries over.

What a client hears. Each order gets ACCEPTED or REJECTED with a reason, and a cancel gets CANCELED. At the clear each order gets its FILLs and an ORDER_DONE, a lapsed order too, and the batch ends with BATCH_DONE. If the clear cannot be done (the solver ran out of its pivot budget, the input was refused, or the optimality check failed) the batch is voided: no fills, one BATCH_VOIDED naming why, and every order lapses, identically on every replica.

HOW THE CLEAR WORKS

The clearing module knows nothing about GPUs. It takes orders expanded into lists of item numbers and returns fills and one price per item that traded. It chooses, in order of importance:

  1. The most welfare: the value of the bids that fill minus the cost of the asks that fill.
  2. Among those, the most units. A trade at zero surplus (bid price equal to ask price) executes.
  3. Among those, the orders that arrived first.

The same input, down to the order of the lists, always gives the same result. That is what lets replicas agree.

The market as a flow

Each order is a node, and so is each item an order lists. A curve step is an arc: its quantity is the capacity, its price the cost (negated for bids), paired with the order's arrival rank, its place in arrival order, for the tie-break. Units flow source → ask → item → bid → sink, so maximizing welfare is a min-cost flow. Every capacity is an integer, so an integer optimum exists. 

source ──▶ ask    one arc per ask step.   capacity = step quantity,    cost = ( +price, arrival rank )
ask    ──▶ item   one arc per offered item.  capacity = the ask's per-slot cap
item   ──▶ bid    one arc per accepted item. capacity = the bid's per-slot cap
bid    ──▶ sink   one arc per bid step.      capacity = step quantity,    cost = ( −price, arrival rank )
sink   ──▶ source the return arc, closing the loop: each unit through it earns more
                  than any difference in rank, so volume outranks the tie-break

One price per item

Many sets of item prices fit the optimal allocation. The clear reports the lowest: the lowest price at which every ask that sold would still sell and no bid that missed out would pay more (in flow terms, a shortest-path distance in the residual graph). Everyone trades at their item's price, so the exchange takes in exactly what it pays out. The cost: with one uniform price a buyer can gain by bidding below its true value, so the mechanism is not incentive compatible (bidding your true value is not always the best play).

Ties go to the earlier order

An order's arrival rank is its position on its side in the gateway's sequence, and a unit costs the sum of its ask's and its bid's ranks. Among allocations with equal welfare and volume the clear minimizes that sum, so ties go to the earlier order. Nothing is random: arrival order is a total order every replica already shares. Ties never change welfare, volume or prices, only who trades what.

WHY NETWORK SIMPLEX

Network simplex was not the first solver. The first, successive shortest paths (route one more unit along the cheapest path, repeatedly), is now the reference the tests compare against; at 10,000 bids it needs over 30 seconds on most batches. Three other directions were built, tested and benchmarked. The numbers:

  • Primal-dual (one search, then many paths) wins when many shortest paths share a length. With arrival ranks in the cost they are mostly distinct, and it landed within a factor of two of the first solver.
  • Incremental (stay optimal as each order arrives) cost 5 to 140 times one batch solve. Its one gain is a live indicative price, a price shown before the clear, which this exchange does not offer, and a storm of cancels is its main weakness.
  • Threads help only when the market splits into independent pieces, sets of orders that share no items. With one accepted item per order, 10,000 bids fall into 2,390 pieces; with two per bid, one piece holds 99.6 percent of the orders.

Network simplex keeps a spanning tree, brings in an arc that improves the cost, pushes flow round the cycle it closes (one such step is a pivot), and stops when none improves. Ties and the price range do not matter to it. Which improving arc to bring in is the pivot rule. The textbook rule (block search) scans the arcs in blocks of consecutive arcs and takes the best arc of the first block that holds an improving one. At 10,000 bids it clears ERCOT-shaped order books in about 20 milliseconds to about a second. ERCOT, the Texas grid operator, runs a real batch auction with curve bids (its day-ahead power market), and five days of its bids set the shapes of the synthetic batches used here.

Batches built to be hard

Orders are capped, but arcs are what the solver pays for: without a limit 10,000 bids could reach millions of arcs, so a batch has an arc budget and each buyer an arc quota. The pivot rule is part of the protocol

Arcs are added order by order, so a textbook block covers a handful of orders, and where few items are wanted by many orders it took millions of pivots: four such batches took 8 to 122 seconds. The production rule scans chunks of 128 arcs spread over the whole array, at a stride of about 0.618 of the chunk count (made coprime with it), and those four batches take 2 to 3 seconds. Across 55 other shape-and-seed cases the total fell from 71 s to 13 s and none was slower; one shape outside all of these got worse, the chain batch above, from 0.04 s to 0.64 s.

Welfare, volume, rank sum and every traded item's price are properties of the input, so every correct solver returns them. Which of several equally good allocations comes back depends on the pivot rule and the order arcs were added in, so replicas must run identical solver code, and a change ships like a protocol change.

Integers only

Quantities are node-hours, prices are whole ticks, and all arithmetic is exact integer.

BUYS Replicas on different CPUs cannot round differently, and a replay reproduces a clear bit for bit.

COSTS A price is a whole tick of $0.01, at most 220 − 1 ($10,485.75).

Arrival order breaks ties

The clear minimizes the total arrival rank of the units that trade.

BUYS A total order every replica shares keeping solves deterministic

COSTS Early submission wins ties, a cancel-and-resubmit loses its place, and a sum of ranks is not strict priority: in rare multi-unit cases the two differ.

Clearing/ · ClearingInput::bidRank

The minimal optimal price

Every buyer pays, and every seller receives, the lowest price that supports the allocation.

BUYS A price set by the market, not by which equal allocation came back. The exchange takes in exactly what it pays out.

COSTS Not incentive compatible: shading a bid below true value can pay.

Clearing/ClearingImpl.hpp

A certificate on every clear

After the last pivot, one pass checks flow bounds, conservation and complementary slackness on every arc.

BUYS Together those conditions are a checkable proof of optimality, so a bug in the pivot code cannot allow a wrong allocation.

COSTS One more pass over the arcs, and a failed check voids the batch.

SimplexCore::verifyCertificate

Work bounded in pivots, not seconds

Orders that would take a batch past 1,000,000 arcs are rejected. A clear that needs more than 4,000,000 pivots stops, at the same pivot on every replica.

BUYS A batch that cannot be cleared is voided identically everywhere; pivots, unlike seconds, depend on the input alone.

COSTS A pivot cost 2 to 14µs in testing, so the budget allows a stall of 8 to 56s, and a void costs everyone the hour. The most any batch has needed is 0.55 million pivots (925,341 arcs, 2.0s).

Limits.hpp · MAX_CLEAR_PIVOTS

The solver is part of the protocol

The pivot rule, the chunk sizes and the order arcs are added in decide which equal allocation comes back, so every replica runs identical solver code.

BUYS Replicas never disagree.

COSTS A solver change is a planned down window.

Tests/GoldenTests.cpp

Quotas that add up to the limits

A buyer may hold 20 open bids, make 200 submissions and use 980 arcs. With at most 500 buyers these add up exactly to the limits on bids and submissions, and, with 510,000 arcs reserved for asks (51 at most each), to the 1,000,000-arc budget.

BUYS A buyer inside its quota never meets a full batch.

COSTS Quotas key on a participant id the client simply asserts. They stop an honest client overloading the clear, not one that makes up ids.

Limits.hpp · BatchBook::admit

Recorders recompute, they do not listen

Replicas that never lead re-run the clear from the log and write the results, instead of tapping the egress (the leader's outbound events).

BUYS Nothing lost on the lossy egress is missing from the record, and two files that agree are a free determinism check.

COSTS One more solve per batch per recorder, and a recorder that dies cannot catch up once the gateway's ring (its fixed-size store of recent commands) has wrapped.

WHY THIS DESIGN, AND WHAT WAS LEFT OUT

Every feature of the clear (substitution across models, regions and hours, per-slot caps, curves, fills that mix models) keeps it a min-cost flow, and a min-cost flow comes with exact integer answers, an optimality certificate and prices that support the allocation. All-or-nothing orders, contiguous hours (the same node for several hours in a row), exchange rates between models, single-model fills all break this constraint.

Hourly slots are also a common base product. Day-ahead power auctions take orders period by period; a block over several periods is an add-on, accepted whole or not at all. Blocks need integer programming, uniform prices often do not exist with them, and a block priced to trade can still be rejected. SF Compute, a GPU-compute marketplace, has an order API that lets a buyer opt into partial fills covering part of the window in disjoint pieces, which is what this exchange does. The cost: a buyer who needs two hours in a row can name both, and may get only one.

FROM THE CLEAR TO A RECORD

Results leave the exchange by two routes, and only one of them is the record.

  • The egress is best effort. Only the leader publishes results to clients, as UDP datagrams that each carry a batch of events, and a lost datagram is not sent again (no gap-fill). Measured on one machine, a clear that emits about 78,000 events reached one client whole in three runs of ten and in part in the other seven, BATCH_DONE included in those; see Known limits.
  • The recorders recompute. A recorder is a replica that never leads. It reads the same log, runs the same engine and writes each batch to its own SQLite file; it never hears a result, it derives it again. A client that missed its ORDER_DONE asks the API.

The recorder and the API

  • One transaction per batch (SQLite in WAL mode, synchronous=FULL), so a reader sees all of a batch or none of it. The first record of a batch id wins.
  • A SHA-256 digest per batch. The API says whether the recorders' files agree on a batch, and verify=1 recomputes the digest from the stored rows. A repeat of a batch id whose digest differs is logged. A void is recorded with its reason, and a recorder that cannot record exits rather than skip a batch.
  • The file holds batches, orders (what each asked for and got), fills, accelerator_prices and open_orders. Prices are summarized per model and hour (units, money, the cheapest and dearest item price), never per interconnect or region, so a price series has one row per hour. Cancelled orders, and the orders of a voided batch, are not recorded.

ResultsApiApp is a separate process that opens each recorder's file read-only and serves JSON over GET: /status, /batches, /batches/{id}/orders, /fills, /prices, /participants/{id}/orders. It listens on 127.0.0.1 and has no authentication. Every answer carries a watermark for each recorder (the latest batch it has written), so a client that finds nothing can tell “not there” from “not yet”. Open orders are sealed: with no authentication, anyone who could reach the API could read other buyers' unfinished curves and bid one tick above the best, so /participants/{id}/open_orders answers 403 unless the operator starts it with --open-orders.

MEASURING IT

Core gives every command a 64-byte trace with four timestamps and four opaque counters, and forwards each finished trace to a performance service over UDP (see the Core page). BatchGPU domain specific telemetry: lifted units, bids filled, bids unfilled and solver pivots, on the clear's trace.

Not captured: the time until a client has its acknowledgement (Core does not stamp the egress); refusals by reason; cancels; a clear longer than about 1.07 s or a counter over 1,000,000 (the ranges of Core's histograms); and an order's arrival time in the results, which keep its arrival rank instead. These are limitations that will be addressed in Core v2.

KNOWN LIMITS

Things a careful reader would find, stated up front. The pipeline's own limits are on the Core page.

NO AUTHENTICATION The gateway trusts the participant id an order claims, and accepts a BATCH_CLEAR with any batch id from any connection. The results API listens on 127.0.0.1, and its open-orders route is off unless started with --open-orders.
A RESTART LOSES THE OPEN BATCH The gateway's sequenced log does not survive a restart, so the orders waiting for a clear are lost. The replicas and recorders must be restarted with it: they take the restarted gateway's commands for duplicates and ignore them, as a test showed. A replica or recorder started or restarted alone catches up on its own from the gateway's log, by the same test, but it replays from the first command, so only while the gateway's ring (1,048,576 commands) still holds it. A new solver build is a planned down window right after a clear.
REPORTING IS BEST EFFORT Replica-to-gateway UDP has no gap-fill, so a client can miss some of a large clear's results. Across ten runs of a clear that emits about 78,000 events, one client received every event in three and only part in seven; it always had the first 17,500 acknowledgements. The gateway's own counters showed no event missing from the replicas and no client output dropped, yet it had delivered only 29,560 to 74,278 of the events, so Core's statistics do not show this loss. It is not the gateway's 1 MiB limit on a client's unsent output: 16 MiB changed nothing in three runs. The cause is not known. Every result is in the recorders' files and the API, which is where a client asks for one it missed. Telemetry is UDP too, and its histograms stop at about 1.07 s and 1,000,000: a longer clear or a larger count is dropped, uncounted.
ORDERS BEHIND A CLEAR WAIT FOR IT A replica's inbound queue holds 1,024 commands, and the clear holds it for as long as it runs. Orders sent right behind a clear fill the queue, and the receiver stops reading until the clear ends, so they wait in its socket buffer: with Core v0.3.0's 4 MiB buffer they fit, and in all ten runs every order was recorded and the two recorders wrote identical digests. The median order reached the engine 0.44 to 0.51 s after the gateway took it. The kernel still dropped 75 to 1,988 UDP datagrams during those runs, counted for the whole machine, and a receiver fetches what it missed from the gateway after 200 ms without a datagram. No run has sent a clear while a burst was still being recovered.
SINGLE GATEWAY The ticker, sequencer, retransmit server, arbiter and egress gateway share one process. Matching and recording are replicated; the front door is not.
A TOY MARKET Five models, one node size, no exchange rates, no contiguous multi-hour blocks (planned research). The exchange clears and records: it does not deliver compute, verify hardware, take payment or track what capacity a seller has already committed. One uniform price per item is not incentive compatible.
FIXED LIMITS 10,000 live orders and 100,000 submissions a side (cancelled orders count as submissions); 500 buyers a batch; 1,000,000 arcs and 4,000,000 pivots a clear. A batch that runs out of pivots is voided. The results file is never pruned.
LINUX ONLY Core uses epoll, mmap and multicast sockets directly. On Windows, build under WSL.

BUILD AND RUN

The first configure fetches Core, googletest and SQLite 3.53.4. 

cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
ctest --test-dir build --output-on-failure

Bench/run_sweep.sh                 # every cell killed after 30 s, reported as "> 30 s"
GEN=realistic Bench/run_sweep.sh   # the same sweep on ERCOT-calibrated batches

Start the replicas and the recorder, then the gateway. The gateway's ticker sends a clear as soon as it starts and then one at half past each hour; --no-ticker leaves the clears to a client. Client/BatchClient is a small command-line order-entry client. It stays connected from the order to the clear, because results go back to the connection that sent the order, and it prints every event that arrives. To see a batch clear without waiting for the half hour, start the gateway with --no-ticker and run the client's demo command, which enters an ask and three bids and clears them. With the ticker on, leave out --batch: the open batch follows the clock. The client is not covered by the tests. The frames it sends are in NetworkService/BatchWire.hpp. For load, Core recommends receivers that spin (--ingress-spin-micros 100 on the replicas and the recorder) and no console line per event (--no-console-echo on the gateway), with net.core.rmem_max at 4 MiB or more on the host. The replicas, the recorder and the gateway must be built against the same Core version.

    OVERVIEW

    EventContractLOB is a limit order book for binary-outcome event contracts: prices are whole cents from 0 to 100, and clients enter orders over real NASDAQ OUCH 4.2 framing. It is a portfolio project, not a production exchange.

    It doesn't implement its own networking, replication or failover. Those come from ToyExchange Core, a product-agnostic pipeline: this repository is what a product has to supply to use it — a protocol handler, a command, an engine, and an event encoder. This page covers only those pieces; the sequencing, gap recovery, leader election, fencing and timing machinery are described there.

    OUCH IN, EVENTS OUT

    Ingress

    A frame is [2-byte big-endian length][1-byte message type] followed by the real OUCH 4.2 struct. The length envelope is this project's own transport framing — real OUCH runs over SoupBinTCP, which isn't implemented — and only what follows the type byte is byte-accurate to the spec. Three message types are handled: O (enter), X (cancel) and U (replace).

    • What closes a connection. A frame whose length is wrong for its type, or a type byte that isn't one of the three. Nothing downstream could parse it.
    • What gets rejected instead. A well-formed frame with bad content becomes an INVALID command and flows through the normal pipeline to a reject, without dropping the connection: an unknown symbol, a price above 100 cents, or shares outside 1–999,999 (OUCH's "greater than 0, less than 1,000,000"). The same checks run again inside the book, so nothing that bypasses the handler can rest an out-of-range order.
    • Price. OUCH's fixed point is dollars × 10,000, so 4200 is $0.42; dividing by 100 gives cents exactly. A sub-cent remainder is truncated rather than rejected — this exchange can't represent it, and rejecting real OUCH precision would defeat accepting unmodified clients.
    • Order type. Real OUCH has no order-type byte, so the type is recovered from timeInForce: 0 means immediate-or-cancel, 99998 ("market hours") means good-till-day, anything else is a plain limit order. That makes only three types reachable over the wire — limit, IOC and good-till-day. Fill-or-kill, market and good-till-cancel exist in the engine and are covered by book-level tests.
    • Firm. The 4-character market-participant code is packed into an integer, which drives self-trade prevention.
    • Tokens. Each order token maps to an order id so cancel and replace can find their target. A cancel for an unknown token is accepted and does nothing: a cancel racing a fill is routine, not a protocol error. A replace inherits side, firm and type from the order it replaces.

    Egress

    The engine emits an event for every state change. Core's egress gateway encodes each one once and sends the same bytes to the originating client (private ack) and to the public group. The frame is a custom compact layout, not ITCH: 

    [2B BE length][1B type][8B order id][1B side][1B price][4B qty][4B leaves qty][8B match id][1B reject reason]
type: A accepted · J rejected · E executed · C canceled · U replaced · D deleted (declared, never emitted)

    THE BOOK: HOW ORDERS MATCH

    One book per replica process. Bids and asks each have 101 price levels, and within a level orders queue first-in first-out, so priority is price then time.

    OrderWhat it does
    LIMIT / GOOD_TILL_CANCELTrades against everything that crosses at its limit price or better, then rests any remainder.
    GOOD_TILL_DAYLike a limit order, and if any of it rests, schedules an end-of-day cancel (below).
    IMMEDIATE_OR_CANCELTakes what crosses at its limit or better; the remainder is canceled (a CANCELED event with nothing left).
    FILL_OR_KILLFirst counts the qualifying liquidity. If it isn't enough, the order is rejected with INSUFFICIENT_LIQUIDITY and nothing trades — not even the part that could have.
    MARKETSweeps whatever is there at any price; the remainder is canceled.
    Cancel (wire X)Removes a resting order and reports it canceled with nothing left. An unknown or already-filled order is a safe no-op.
    Replace (wire U)Cancels the old order and enters a new limit order under a new id, acknowledged as REPLACED. The new order goes to the back of the queue. An unknown id is rejected with UNKNOWN_ORDER.

    The rules that hold for all of them

    • Trades print at the resting order's price. A bid at 60 that meets an ask at 50 trades at 50, on both legs.
    • Every fill is two events — one per side — sharing a match_id, and event sequence numbers only ever increase.
    • Self-trade prevention is a hard stop. If the next resting order at the front of the line belongs to the aggressor's own firm, the aggressor's remainder is rejected with SELF_TRADING_PREVENTION and the resting order is left alone. Fills against other firms that came earlier in the queue still happen first. Fill-or-kill's liquidity count applies the same stop.
    • Every rejection names its reason: unknown order, invalid quantity, self-trade, insufficient liquidity, price out of range, unknown symbol.

    Timed cancels

    A GOOD_TILL_DAY order that rests asks a small service to cancel it at the end-of-day cutoff. That service is just another OUCH client of the gateway: when a cancel comes due it sends an ordinary cancel over TCP, so the cancel is sequenced and replicated like any other command. It only sends while its own replica believes it is leader, so a standby's copy stays quiet. The cutoff is a fixed UTC−5 offset (see limits).

    WHAT REPLICATION ASKS OF THE BOOK

    Replication, gap recovery and failover are Core's job (see the Core project). The book's part is to be something replicas can run independently and still agree:

    • Matching is a function of the command stream. No matching decision reads a clock or a random source. The wall clock appears as a timestamp on outgoing events and, for good-till-day orders, in the cutoff time handed to the cancel service — neither changes what trades.
    • Counters are local and deterministic. Match ids and event sequence numbers each start at 1 and only increment, so replicas fed the same commands produce the same ids.
    • Timed actions re-enter through the gateway — the cancel service above — instead of firing locally.
    • Standbys still run the book. Every replica matches every command; only the leader's events are published.

    THE BOOK'S DATA STRUCTURES

    These are the latency choices that belong to this product. The pipeline-level ones — lock-free rings, busy-polling, single-writer sequencing, the memory-mapped store — are on the Core page. Each card lists what the choice gives up alongside what it buys.

    Price ladder indexed directly by price

    101 price levels in a fixed array; a price is the index.

    BUYS O(1) access to any level, no hashing, no tree.

    COSTS Only works because the price domain is tiny (0–100 whole cents). A wide-tick market would need a different structure.

    MatchingService/OrderBook.hpp · MAX_LEVELS

    128-bit occupancy bitmap for best bid / ask

    Two 64-bit words mark which levels hold orders; best ask is the lowest set bit (ctz), best bid the highest (clz).

    BUYS Best price without scanning levels — at most two word checks.

    COSTS The bitmap must be kept in sync whenever a level becomes occupied or empty. After the best level, matching still steps one price at a time (at most 101 steps).

    OrderBookBits · find_first_level / find_last_level

    Pre-allocated order pool with a free list

    Each side owns 262,144 order slots up front; inserting pops a free slot, filling or canceling pushes it back.

    BUYS No heap allocation on the matching path.

    COSTS A hard cap per side. When the pool is empty, insert_order throws std::runtime_error.

    BookSide · BOOK_POOL_SIZE, m_free_pool

    Intrusive FIFO list per price level

    Orders link to each other by pool index (prev/next), with a head and tail per level.

    BUYS O(1) append, O(1) removal from the middle, and price-time priority for free.

    COSTS Walking a deep level chases links through memory. measure matching cost against level depth

    PriceLevel · Order::m_prev_idx / m_next_idx

    Flat order-id lookup table

    A vector of 10,000,000 order pointers, indexed by order id.

    BUYS O(1) find for cancel and replace.

    COSTS About 80 MB reserved up front, and it assumes ids stay below 10,000,000 (the replace path checks; see limits).

    OrderBook · MAX_GLOBAL_ORDERS

    A size budget for the pooled order

    The order record is asserted to stay within 56 bytes.

    BUYS Pool slots stay small and dense, so more of a level fits in cache.

    COSTS Adding a field to an order can break the build (static_assert) and forces a decision about what to trade for it.

    MatchingService/Order.hpp

    Two counters per order

    As the book walks price levels it counts the levels touched and the resting orders visited, in two of Core's opaque counter slots (LobExtSlot). They reach the aggregator as ExtCounter0 and ExtCounter1.

    BUYS Visibility into how much matching work each order caused, alongside how long it took.

    COSTS Two increments inside the matching loop. measure what they cost A test checks a two-level, three-order sweep bumps them by exactly 2 and 3.

    TESTS

    83 test cases at the time of writing, run by ctest and in CI. They cover:

    • Matching semantics — priority, sweeping several levels, the trade-price rule, and each order type's behavior at the edges (empty book, partial liquidity, limit-price cutoffs).
    • Self-trade prevention — including that earlier fills against other firms still happen and that a fill-or-kill's liquidity count stops at the firm's own order.
    • Validation — out-of-range prices, zero and oversized quantities (the limit is inclusive at 999,999), unknown symbols, unknown orders, on both the wire and book paths.
    • Cancel, replace and timed cancels — including a rejected replace leaving the original order untouched, and scheduling under the new token after a replace.
    • The OUCH wire path — frames over a loopback TCP connection through Core's real gateway and multicast receiver, malformed frames closing the connection, content errors not doing so.
    • Pipeline behavior through this product — gap recovery, an unrecoverable gap, trace-arena collisions, and leader-gating of timed cancels (Core has no protocol-agnostic stand-ins to test these with on its own).

    By hand: Tools/two_replica_smoke_test.sh runs a gateway and two replicas and checks that the books converge, that exactly one replica publishes, that the epoch strictly increases after killing the leader, and that the survivor's output still arrives.     KNOWN LIMITS

    Product-level limits; the pipeline's are on the Core page.

    CAPACITY CEILINGS Each book side holds at most 262,144 resting orders (insertion throws beyond that), and the order-id table has 10,000,000 entries. The replace path bounds-checks an id against the table; the plain insert path does not. decide and document what happens past 10 million orders in a day
    GTD CUTOFF The end-of-day cancel time is a fixed UTC−5 offset, not daylight-saving-aware Eastern time, so it is an hour off for most of the year. The code says so in a comment; the build's standard library lacks the time-zone database.
    PRICE DOMAIN Prices are whole cents from 0 to 100. The book's direct-indexed ladder depends on that; it is not a general price structure.
    ORDER TYPES OVER THE WIRE Only limit, IOC and good-till-day can be entered over OUCH, because timeInForce is the only order-type signal it carries. The other types are engine-level and tested there.
    ONE BOOK One book per replica process. Symbols are validated against a registry but don't select between books.
    EGRESS FORMAT The public feed is a custom compact frame, not ITCH, and the DELETED event type is declared but never emitted (a full cancel reports CANCELED with nothing left).

    BUILD AND RUN

    Linux only (it uses epoll, mmap, multicast sockets and CLOCK_TAI directly); on Windows, build under WSL. The build fetches Core from GitHub, pinned to a release tag.

    cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j"$(nproc)"
ctest --test-dir build --output-on-failure

# gateway + 2 replicas + performance service
./run_exchange.sh 2 build

# from another shell: two crossing orders
build/Tools/OuchTestClient/OuchTestClient --side B --price 50 --qty 10 --firm-id 1
build/Tools/OuchTestClient/OuchTestClient --side S --price 50 --qty 10 --firm-id 2 --listen-ms 500

# kill only the current leader and watch the survivor take over
./kill_leader.sh run
tail -f run/performance.log

OVERVIEW

This is a portfolio project, not a production exchange

Core implements generic functionalities that an exchange might want like networking, fault-tolerance, and measurements. The Core idea is that a matching engine fits neatly into the design, whether the product on top is a limit order book, an auction, or something else.

Core's design philosophy is based on the LMAX Disruptor's mechancial sympathy to achieve high throughput and low latency through lock free SPSC ring buffers. Core includes a sequenced and replicated input, a leader-elected matching tier with real failover, and a measurement path.

What is in the repository

  • Core/ — a header-only CMake library: ingress, egress, replica arbitration, the generic replica host, the SPSC queue, and telemetry.
  • PerformanceService/ — monitors the exhanges health through telemetry, consumed via HdrHistogram percentiles.
  • Benchmarks/ — opt-in tools (-DTOYEXCHANGE_BENCHMARKS=ON). IngressBench runs the real gateway and receivers over a chosen transport. The Aeron comparison below used it.
  • No product logic. Products consume this repository as a dependency (CMake FetchContent, pinned to a release tag).

Outside Product Implementations: EventContractLOB, a level 3 continuous limit order book for binary-outcome event contracts using the NASDAQ OUCH protocol. BatchGPU, an hourly batch auction for trading GPU compute capacity.

LIFE OF A COMMAND

What happens between a client's TCP send() and the acknowledgement coming back. Steps marked (product) are the products resonsibility to implement.

  1. Parse and validate (product). The gateway's single ingress thread reads the socket via epoll and hands the bytes to the product's protocol handler. A frame that cannot be interpreted closes the connection. A well-formed frame with bad content becomes a command the product marks invalid and later rejects, without dropping the connection.
  2. Sequence. The ingress thread stamps a monotonically increasing sequence number from a plain counter. The same number doubles as the telemetry trace id. It also records the socket-read time and which client session sent the command.
  3. Append, then send. The sequenced message is written into a memory-mapped ring (SequenceStore) before it is multicast, for possbile retransmission.
  4. Fan out. One UDP multicast sendto() up to one datagram's worth (1,400 bytes by default), to every replica.
  5. Receive and check. Each replica's receiver thread compares the sequence number with the one it expects. A gap triggers recovery (below), and a number older than expected is a duplicate and is dropped. In-order messages are pushed into the replica's inbound SPSC queue.
  6. Match (product). A matching thread spins on that queue, pops a command, performs the matching algorithm, then pushes an event into an output SPSC queue.
  7. Publish (leader only). Each replica's egress publisher drains that output queue. Only the replica that believes it is leader multicasts them, as one datagram that starts with an EgressBatchHeader: its fencing epoch, the ordinal of the first event, and the number of events. Nothing waits for a datagram to fill, so an event that arrives alone goes out at once. Every replica numbers every event, published or not. Replicas are deterministic, so no data is lost internally.
  8. Fence and deliver (product encodes). The egress gateway discards any datagram whose epoch is older than the arbiter's current epoch. Privately, each client gets its frames from one datagram in one write on its own TCP connection. A client that has since left is skipped, and a client whose socket is full has its output kept, in order, up to a limit. Publicly, the frames go back to back into datagrams of the same size limit on the broadcast group.

FAULT TOLERANCE

Three mechanisms to keep trading alive: a shared sequenced input, gap recovery, and epoch-fenced leadership.

1 · One ordered input, many identical books

Replicas never talk to each other. Each one applies the same sequenced command stream to its own engine, so their state follows from the input alone.

RULE Every product built on Core must be deterministic. Core relies on this for replay (late join and restart) and stateless failover. A product abide by the following:
  • Nothing that affects state depends on hash-container order, pointer values or randomness.
  • Nothing that affects state depends on a floating-point result that can differ between hosts.
  • A clock reading may stamp an emitted event. It must never feed back into state.
  • The command stream is the only input. Anything that must affect every replica enters through the gateway as a sequenced command -- examples: a timed cancel, or BatchGPU's batch clear.
  • A command that makes the engine throw must throw on every replica.
NOTE Core does not check that an engine is deterministic, and it does not compare the replicas' state.

2 · Lost packets, gap detection, and retransmission

UDP multicast is presumed lossy by core. Every replica tracks the next sequence number it expects. When a higher one arrives it asks the gateway's retransmit server for the missing range over a UDP request/response, pushes the recovered records into its queue in order, and only then processes the live message that revealed the gap. Requests are capped at 500 records per batch. A lost, repeated, late or partly stale datagram is ignored or trimmed, so it can never take another record's place.

If a replica hears nothing for a full 200 ms receive timeout, asks for new messages; NOT_YET_ARRIVED means it is caught up. The sequence store is a ring, so old entries get overwritten. If a range can never be filled, and the replica stops itself (exit code 2).

3 · Leadership and fencing

Every replica sends a heartbeat to the gateway's ReplicaArbiter every 2 ms, carrying its id and the last sequence number it applied. The arbiter replies with the current {epoch, leaderId}. A replica is eligible to lead if its last heartbeat is fresh (default: within 10 ms) and it has reached the highest sequence number that any replica reported. On leader turnover, the lowest-numbered eligible replica takes over. The epoch is bumped on every leadership change, including to or from "nobody". Egress checks epoch and drops stale messages.

TELEMETRY

Every command gets a 64-byte, cache-line-aligned OrderTrace record in a fixed arena of 220 slots (64 MiB), indexed by its sequence number. Four timestamps are written as the command progresses, and the matching thread never does I/O for measurement: finished traces go into a queue and a separate thread forwards them over UDP.

Aggregating Traces

  • Every replica reports to PerformanceServiceApp, wrapped with its replica id. Reports are deliberately not fenced by epoch to see overall system health
  • The aggregator constructs the HdrHistogram for real-time visibility. A trace with an incomplete timestamp pair is ignored rather than recorded as garbage.
  • Resting commands report late. A trace completes when its command leaves the engine, so a long-resting order's sample can land many windows after it executed. The rolling view merges the retained windows to smooth that out.

TRADING THINGS AWAY FOR LOWER LATENCY

Every choice below buys lower or more predictable latency by giving something up.

SPSC rings, cache-line separated

Power-of-two capacity (mask, not modulo); head and tail each on their own 64-byte line; acquire/release atomics; no locks or CAS.

BUYS Producer and consumer never contend on a cache line or a lock.

COSTS Strictly one producer and one consumer per queue, so the pipeline is a chain of single-threaded stages. Capacity is fixed: a full queue stalls its producer.

Core/SPSCQueue.hpp

Busy-polling matching thread

The matching thread spins on try_pop with no sleep or yield.

BUYS No wake-up latency when a command arrives.

COSTS A core at 100% even when idle.

PINNING The code does no CPU pinning or scheduler tuning. However, pinning should help reduce latency.

Core/MatchingService.inl · poll()

Single writer ingress

One ingress thread assigns sequence numbers from a plain counter and is the only writer to the store.

BUYS Ordering with no atomics, locks or coordination.

COSTS Ingest throughput is bounded by one thread, and the gateway is a single point of failure (see limits).

Core/Ingress/NetworkGateway.inl

Append first, then multicast once

The message is written to the store before a single UDP datagram serves all replicas.

BUYS Cost independent of replica count; nothing a replica misses is unrecoverable within the ring's horizon.

COSTS UDP loses packets, so recovery logic is required, and history is bounded by the ring.

NetworkGateway::pollSockets · SequenceStore

Seqlock slots in a memory-mapped ring

Each slot carries a version counter (odd = being written). The retransmit thread reads without ever blocking the writer.

BUYS The ingress writer never waits for a reader.

COSTS A reader may retry (4 attempts) and, if contended, report the record as too old. The file is mapped with MAP_POPULATE and locked with a best-effort mlock.

Core/Ingress/SequenceStore.hpp

Plain structs on internal channels

Sequenced messages, heartbeats, retransmit requests and egress batches (a fixed header, then raw events) are plain structs sent as raw bytes — no serialization layer.

BUYS No encode/decode work between gateway and replicas.

COSTS Those channels assume identical struct layout and byte order on every host. Explicit encoding is left to the product's own wire protocol.

SequencedInboundMessage · EgressBatchHeader

Telemetry off the critical path

The matching thread only writes timestamps into its own arena slot; a separate thread forwards finished traces over UDP.

BUYS Measurement adds a few stores and clock reads to the hot path, not I/O.

COSTS If the trace queue is full the trace is dropped (engine events are never dropped).

SPSCProducerPolicy · TelemetryForwarder

Two clocks

rdtscp for timings that stay on one machine; CLOCK_TAI for anything that may be compared across machines. TAI has no leap seconds, so it can't step backwards the way CLOCK_REALTIME can.

BUYS Cheap local timing, and cross-machine deltas that don't go negative.

COSTS Cross-machine numbers are only as good as the clock sync. Core uses PTP for clock synchronization; no plans to adopt white rabbit.

Core/Telemetry.hpp · Tools/ptp/

Opaque counters

Each trace reserves four 32-bit slots that Core carries and windows but never interprets. The product decides meaning.

BUYS Core stays product-agnostic, and PerformanceServiceApp needs no per-product build.

COSTS Generic names (ExtCounter0…) in the output, a fixed count of four, and slot meanings documented on the product's side. Templating the trace on a product type would force product specific aggregators.

OrderTrace · MetricKind::ExtCounter0…3

Cache-line-sized records

OrderTrace and each sequence-store slot are 64-byte aligned.

BUYS One record per cache line; no false sharing between neighbours.

COSTS A field change that crosses 64 bytes doubles the arena's footprint — the build fails on purpose when it happens (static_assert on OrderTrace).

Telemetry.hpp · SequenceSlot.hpp

WHY NOT AERON

Aeron is a high-performance message passing system which seems like a great fit for Core, so why is it not used? I built a second transport on Aeron 1.53.3 (its C media driver and C++ client) and ran both through the same benchmark. The benchmark uses the real gateway, a TCP client that sends at a fixed rate, and a consumer thread on each replica. The harness is in the repository's Benchmarks/ directory.

Why the hand-written transport stays

  • It was not slower. Over UDP, Aeron's median latency was 63 to 73 µs against 38 to 48 µs at 500,000 commands/s, and the two have the same ceiling here.
  • It does not replace the store. A late or lagging replica cannot catch up from an Aeron stream. Using Aeron would mean keeping the sequence store and retransmit server anyway, so there would be two recovery paths for one problem.
  • A custom flow control would only recreate half of it. Aeron lets you write one, and one could keep a slow replica from holding the sequencer back. That is the property the hand-written design already has. Catching up is a separate problem that flow control cannot solve. The plug-in would also run inside the media driver and depend on its internals.
  • It adds a process per host and a decision about spinning. The fast driver settings keep one to three cores busy even when idle.
  • Where Aeron would earn its place: links between processes on one host, where shared memory is far faster, and the Archive if replay needs to outlive the sequence store's ring.
LIMITS OF THIS TEST One machine under WSL2, so tail latencies include hypervisor noise. No tuning besides a few driver settings. The result is for this design on this setup, not a general claim about Aeron.

Why the egress rework?

  • Leadership under load (fixed by the egress rework). Before the rework the leader changed 47 to 84 times in every run from 100,000 to 500,000 orders/s. The cause was the leader's publisher, which sent each event as its own datagram. That many system calls could not keep up, so the event queue (16,384 slots) filled and the leader's matching thread blocked on it. The leader then fell lagged too heavily which the arbiter noticed and set a new leader. The old leader caught up, and the cycle repeated about every quarter of a second. Widening the arbiter's windows to 100 and 200 ms did not stop it, because the lag was real. And after the rework the inbound queues, which had filled behind the blocked matching thread, no longer fill. Now a datagram carries every event that is waiting. At 100,000 orders/s the publisher sent 233,827 datagrams for 2,959,738 events (13 events each on average), and the leader changed in 1 run of 21 with a failover time of 10.7ms.
  • Waking sleeping replicas. The gateway's ingress thread was at 90% and 93% of a core, the busiest thread in its process with 91% of its time in the kernel and churning through only 323,000 orders/s with default settings. Receivers that spin for 100 µs achieved 500,000 orders/s in seven runs out of seven.

KNOWN LIMITS

SINGLE GATEWAY The sequencer, sequence store, retransmit server, arbiter and egress gateway all live in one process and are not fault tolerant by default.
STORE IS A BUFFER The sequence store is file-backed but is zeroed every time the gateway starts, and the sequence restarts at 0. It works as a bounded retransmit buffer for live replicas, not as crash-recovery storage. A running replica that sees the sequence start over ignores those early commands (it logs a warning for each) rather than apply them again, so replicas must be restarted along with the gateway.
RESTART / LATE JOIN A fresh replica starts by expecting sequence 0 and catches up by retransmit, replaying the whole history in order. This is tested, including on a quiet exchange where no live message ever arrives. It works only while the newest sequence number is at most the ring capacity minus one (220 − 1 by default); one more message evicts sequence 0, and the replica stops itself.
ELECTION MODEL Leadership is decided by a central arbiter with a fencing token, not by a consensus protocol among the replicas. The arbiter recomputes only when a heartbeat arrives.
EGRESS GATEWAY CAPACITY One thread receives, encodes and delivers every event. Tuned, the thread used about half a core at 500,000 orders/s and lost no messages but can be overwhelmed if flow increases.
IDLE COST Three threads per replica spin at 100% whether or not any traffic arrives, so two replicas keep about six cores busy at idle. That is the price of the busy-polling design, and it is not tuned or pinned.
TRACE ARENA The arena has 220 slots. A command that rests long enough for the ring to wrap loses its timing record; a collision counter makes that visible but can't prevent it.
SCOPE One engine per replica process. Every measurement on this page comes from one machine under WSL2, with every process on the same host.

BUILD AND TEST

Linux only (it uses epoll, mmap, multicast sockets and CLOCK_TAI directly); on Windows, build under WSL. On its own this repository builds Core and the aggregator; to run a whole exchange you need a product on top — EventContractLOB has the launch scripts, and BatchGPU lists the commands to start each program.

cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j"$(nproc)"
ctest --test-dir build --output-on-failure

The benchmarks are not part of the default build. Add -DTOYEXCHANGE_BENCHMARKS=ON to the first command and build the IngressBench target.

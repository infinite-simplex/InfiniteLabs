    OVERVIEW

    ToyExchange is the part of an exchange that doesn't care what is being traded. It takes bytes off a socket, puts every command into one global order, replicates that order to several matching replicas, elects which replica may speak, fences out the ones that shouldn't, and measures how long each command took. It does all of that without knowing whether the product on top is a limit order book, an auction, or something else. It is a portfolio project, not a production exchange.

    The shape is borrowed from the LMAX Disruptor: every stage is a single thread that owns its data, and stages are joined by lock-free single-producer/single-consumer ring buffers, so the path from the socket to the engine takes no locks. (The egress gateway takes one mutex per client per batch, to find that client's socket.) On top of that it adds what a Disruptor alone doesn't give you — a sequenced and replicated input, a leader-elected matching tier with real failover, and a measurement path.

    What is in the repository

    • Core/ — a header-only CMake library: ingress, egress, replica arbitration, the generic replica host, the SPSC queue, and telemetry. Nothing in it names a price, a quantity or a wire protocol.
    • PerformanceService/ — PerformanceServiceApp, which turns every replica's per-command timing into HdrHistogram percentiles.
    • Benchmarks/ — opt-in tools (-DTOYEXCHANGE_BENCHMARKS=ON). IngressBench runs the real gateway and receivers over a chosen transport. The Aeron comparison below used it.
    • No product logic. Products consume this repository as a dependency (CMake FetchContent, pinned to a release tag) rather than living inside it.

    Products built on it: EventContractLOB, a limit order book for binary-outcome event contracts that speaks NASDAQ OUCH, is the reference product. BatchGPU, an hourly batch auction for GPU compute capacity, is the second: its engine holds the open batch and clears it when a sequenced BATCH_CLEAR command arrives, and it adds its own recorders and a results API. Nothing here depends on either.

    LIFE OF A COMMAND

    What happens between a client's TCP send() and the acknowledgement coming back, in the order the code does it. Steps marked (product) are the slots above.

    1. Parse and validate (product). The gateway's single ingress thread reads the socket via epoll and hands the bytes to the product's protocol handler. A frame that cannot be interpreted closes the connection. A well-formed frame with bad content becomes a command the product marks invalid and later rejects, without dropping the connection.
    2. Sequence. The ingress thread stamps a monotonically increasing sequence number from a plain counter. The same number doubles as the telemetry trace id. It also records the socket-read time and which client session sent the command.
    3. Append, then send. The sequenced message is written into a memory-mapped ring (SequenceStore) before it is multicast, so anything a replica might miss can still be fetched afterwards.
    4. Fan out. One UDP multicast sendto() carries every command the gateway parsed in the same pass of its loop, up to one datagram's worth (1,400 bytes by default), and delivers them to every replica. Nothing waits for a datagram to fill: a command that arrives alone goes out at once, in a datagram of its own. The batch grows only when commands arrive faster than the gateway sends.
    5. Receive and check. Each replica's receiver thread compares the sequence number with the one it expects. A gap triggers recovery (below), and a number older than expected is a duplicate and is dropped. In-order messages are pushed into the replica's inbound SPSC queue.
    6. Match (product). The matching thread spins on that queue, pops a command, hands it to the engine, and records how far it has got (lastAppliedSeq). Everything the engine reports becomes an event pushed into an output SPSC queue.
    7. Publish (leader only). Each replica's egress publisher drains that output queue. It takes every event that is waiting, up to one datagram's worth (1,400 bytes by default). Only the replica that believes it is leader multicasts them, as one datagram that starts with an EgressBatchHeader: its fencing epoch, the ordinal of the first event, and the number of events. Nothing waits for a datagram to fill, so an event that arrives alone goes out at once. Every replica numbers every event, published or not. Replicas are deterministic, so an ordinal names the same event on every replica, and the gateway can tell which events never arrived. A follower drains its queue and sends nothing.
    8. Fence and deliver (product encodes). The egress gateway discards any datagram whose epoch is older than the arbiter's current epoch. It encodes the survivors once and sends the result twice. Privately, each client gets its frames from one datagram in one write on its own TCP connection. A client that has since left is skipped, and a client whose socket is full has its output kept, in order, up to a limit. Publicly, the frames go back to back into datagrams of the same size limit on the broadcast group. A consumer of that feed finds the frame boundaries itself, which a self-delimiting protocol such as OUCH or ITCH allows.

    FAULT TOLERANCE

    The design goal is that a matching replica can die, or miss packets, without the exchange emitting duplicate or stale results — and without the survivors needing to be told anything. Three mechanisms carry that: a shared sequenced input, gap recovery, and epoch-fenced leadership.

    1 · One ordered input, many identical books

    Replicas never talk to each other. Each one applies the same sequenced command stream to its own engine, so their state follows from the input alone.

    RULE Every product built on Core must be deterministic. The same command stream, applied in order from sequence 0, must give the same state and the same events on every replica. Core relies on this for replay (late join and restart) and for failover without any hand-over of state. A product keeps the rule by following five points.
    • Nothing that affects state depends on hash-container order, pointer values or randomness.
    • Nothing that affects state depends on a floating-point result that can differ between hosts.
    • A clock reading may stamp an emitted event. It must never feed back into state.
    • The command stream is the only input. Anything that must affect every replica — a timed cancel, or BatchGPU's batch clear, say — enters through the gateway as a sequenced command and does not fire locally.
    • A command that makes the engine throw must throw on every replica.

    Why the books match. The argument has two halves.

    • Same input. The gateway fixes one total order, and each replica applies it from sequence 0, once and in order. Gaps are filled by retransmit before the live message is processed, a duplicate or late datagram is dropped, and a replica that starts late, restarts, or loses the tail of a burst replays what it missed. Core's ingress-recovery tests cover each of those cases. A replica that can no longer reach sequence 0 stops itself instead of running on a partial history.
    • Same function. This half belongs to the product, and Core cannot check it. The rule above is the contract between the two. Each product shows how its own engine keeps it.
    SCOPE This is a contract, not a proof. Core does not check that an engine is deterministic, and it does not compare the replicas' state. A product that wants that check must make it. Two replicas' event streams also match only where the events carry nothing that differs per replica, such as a timestamp.

    2 · Losing packets: gap detection and retransmit

    UDP multicast is lossy, and on one host the usual cause is the kernel's receive buffer. A burst can fill the default 212,992 bytes while the receiver waits for room in a full queue, so the receiver asks for 4 MiB. That makes gaps rarer. It does not remove them, so recovery stays. Every replica tracks the next sequence number it expects. When a higher one arrives it asks the gateway's retransmit server for the missing range over a UDP request/response, pushes the recovered records into its queue in order, and only then processes the live message that revealed the gap. Requests are capped at 500 records per batch. A batch that comes back short is retried up to 3 times, and each retry asks only for the records still missing, so nothing is delivered twice. A reply is a few datagrams, each holding a small header and as many whole records as fit in 1,400 bytes, not one datagram per record. The header names the first sequence number in the datagram, and the replica uses only the records from the next one it needs. A lost, repeated, late or partly stale datagram is ignored or trimmed, so it can never take another record's place.

    A live message is not the only way to find out. If a replica hears nothing for a full 200 ms receive timeout, it asks the same server for everything from its position onward; NOT_YET_ARRIVED means it is caught up. That catches a replica that has just started or restarted, and one that lost the last datagrams of a burst, with no later command to reveal the gap. An unreachable server is not fatal — the probe simply runs again at the next timeout. In the other direction, delivery is in order from sequence 0, so a datagram older than the one expected is a copy of something already applied (a network duplicate or a late, reordered packet) and is dropped with a warning.

    The sequence store is a ring, so old entries get overwritten. If a range has been evicted the gap can never be filled, and the replica stops itself (exit code 2) rather than keep running on state it knows is incomplete. It then stops heartbeating, and the arbiter drops it from leadership exactly as it would for a crash — no extra signalling path. The boundary is exact: a joiner can catch up only while the newest sequence number is at most the ring capacity minus one, because the newest message occupies a slot too. One more message evicts sequence 0.

    3 · Leadership and fencing

    Every replica sends a heartbeat to the gateway's ReplicaArbiter every 2 ms, carrying its id and the last sequence number it applied. The arbiter replies with the current {epoch, leaderId}. A replica is eligible to lead if its last heartbeat is fresh (default: within 10 ms) and it has not fallen behind. Not falling behind means it has reached the highest sequence number that any replica reported one lag window ago (default: 20 ms). The current leader keeps the role while it stays eligible ("sticky"); otherwise the lowest-numbered eligible replica takes over.

    The epoch is bumped on every leadership change, including to or from "nobody". Each published datagram carries the epoch its sender last heard, and the egress gateway — which lives in the same process as the arbiter and reads the epoch directly — drops anything older than the current one. That is what makes a deposed leader's late packets harmless: it doesn't have to notice it lost the job, the sink refuses its traffic anyway.

    What is tested

    • Core's own suite — 69 tests. Replica arbitration (the first heartbeat becomes leader at epoch 1; leadership is sticky and a returning lower id doesn't bump the epoch; the epoch bumps on failover; the lowest eligible id wins; healthy replicas that report at different moments at 500,000 commands/s do not demote the leader; a leader that stops advancing loses leadership only after a full lag window), the synced clock (matches wall time, monotonic), windowed histograms, aggregation (per-replica routing, incomplete timestamp pairs ignored), one end-to-end forwarder → receiver → aggregator test over the wire, ten gateway tests, twenty egress tests, and twenty-six ingress-recovery tests. The gateway tests run the real gateway, receiver and sequence store with a stand-in wire protocol: commands reach a replica in order and are stored; a frame split across reads parses once; each connection gets its own session id; a broken frame closes the connection but earlier frames stay sequenced; every record is in the store before its datagram reaches the network; commands from one read share few datagrams; and a command that arrives alone is sent at once, never held for others. Three more tests cover a client's private output. A client that does not read gets a write that the socket takes only in part finished later, in order, so no frame is cut by the next one. A client that stays behind has its backlog bounded, and the overflow is dropped whole and counted. Output for a session that does not exist is refused without an error. The egress tests run the real publisher, gateway, arbiter and heartbeat clients with a stand-in event, encoder and session gateway: only the leader publishes; a follower keeps draining its queue and sends nothing; a replica that becomes leader publishes from then on, but not what it discarded before, and the gateway counts what it never saw; an event that is alone goes out alone and at once, and events already waiting share datagrams up to the size limit; each client gets its frames for a datagram in one call, in order, and the public feed packs frames into few datagrams; each event reaches its session and the feed in order, and a session that has gone does not stop the feed; the console echo prints one line per event, or none when switched off, and delivers everything either way; the configured receive buffer is applied; an ordinal that arrives twice is counted; events that never arrived are reported, once for a burst, and the rest when the gateway stops; a message from an older epoch is dropped, including a deposed leader's late message after a failover; a short or mis-sized datagram is counted and ignored; and when the leader dies the survivor is told it leads and takes over, with no second copy while both were up. Breaking the fencing check, the leader check, the follower's draining, the way a gateway finishes a partial write, or the loss report's rate limit each fails exactly the tests that should catch it. The ingress-recovery tests run the real sequence store, retransmit server and multicast receiver with a stand-in command type: a datagram of many records behaves like many datagrams of one (records already delivered are skipped, a datagram that starts past the next expected record recovers the gap first, a torn datagram is dropped); the retransmit server answers a range in few datagrams and ends it with one status datagram; a receiver with a spin window delivers in order, still sleeps after a quiet spell, and still probes when idle; late join and restart replay the full history in order; a joiner catches up while the newest sequence number is at most capacity − 1, and one more message evicts sequence 0 and stops the replica; a fake retransmit server that drops the end of a reply, drops datagrams in the middle of a reply, sends every reply twice, or sends a stale datagram that overlaps the next needed record never makes the replica duplicate, skip or reorder a record; duplicated, late and reordered live datagrams are applied once; and the idle probe catches up a late joiner, or the lost tail of a burst, with no live message, resumes at a record lost mid-reply, stops on evicted history, and survives an unreachable server; the receiver applies the configured 4 MiB receive buffer, and a request that the kernel cap clips is reported as clipped. The tests use small rings (1,024 slots) to stay fast; the boundary is the same arithmetic at 220.
    • Stand-ins, not a product. Core's own tests use stand-ins for the wire protocol, the command and the egress event, so none of this machinery depends on a product to be tested. Anything that needs a real wire protocol or a real engine is tested in the product's own repository.

    MEASURING IT

    Every command gets a 64-byte, cache-line-aligned OrderTrace record in a fixed arena of 220 slots (64 MiB), indexed by its sequence number. Four timestamps are written as the command moves through, and the matching thread never does I/O for measurement: finished traces go into a queue and a separate thread forwards them over UDP.

    From trace to percentile

    • Every replica reports — leader or not — by unicast UDP to PerformanceServiceApp, wrapped with its replica id. Reports are deliberately not fenced by epoch: a standby's timing is exactly what you want to see.
    • The aggregator computes the differences once, keeps one histogram per metric per replica, and rolls them over on a shared timer so replicas stay comparable window for window: 1-second windows, 60 retained, HdrHistogram underneath. A trace with an incomplete timestamp pair is ignored rather than recorded as garbage.
    • Resting commands report late. A trace completes when its command leaves the engine, so a long-resting order's sample can land many windows after it executed. The rolling view merges the retained windows to smooth that out.

    PERFORMANCE: TRADING THINGS AWAY FOR LATENCY

    Every choice below buys lower or more predictable latency by giving something up. The costs are listed next to the benefits on purpose. Where a claim would need a measurement, there is a yellow placeholder instead of a number. Choices that belong to one product's data structures live on that product's page.

    SPSC rings, cache-line separated

    Power-of-two capacity (mask, not modulo); head and tail each on their own 64-byte line; acquire/release atomics; no locks or CAS.

    BUYS Producer and consumer never contend on a cache line or a lock.

    COSTS Strictly one producer and one consumer per queue, so the pipeline is a chain of single-threaded stages. Capacity is fixed: a full queue stalls its producer.

    Core/SPSCQueue.hpp

    Busy-polling matching thread

    The matching thread spins on try_pop with no sleep or yield.

    BUYS No wake-up latency when a command arrives.

    COSTS A core at 100% even when idle. Measured with no traffic, on Core v0.2.1: each replica uses about 302% of a core, because its matching thread, egress publisher and telemetry forwarder (identified by start order) all spin at 100%. The gateway uses 3%, so a stack with two replicas uses about 607% of one core out of 16 hardware threads. The optional receiver spin window adds nothing at idle.

    PINNING The code does no CPU pinning or scheduler tuning. I tried pinning each process with taskset (gateway on two cores, each replica on three whole cores plus one sibling thread) at 50,000 orders/s on Core v0.2.1, three 30-second runs each. It made no clear difference. NetworkDelayNs p99 was 530 µs pinned against 649 µs unpinned (medians), with the run-to-run ranges overlapping slightly. The queuing-delay p50 and p99, the queue depth and the engine time matched within the spread. A deliberately crowded control, with every process on two cores, was clearly worse: queuing-delay p99 of 3.8 ms and 8 leader changes, so the comparison can see an effect when there is one. This was pinning by process, not by thread, on a machine with cores to spare; per-thread pinning and busier loads are untested.

    Core/MatchingService.inl · poll()

    Single writer at the front door

    One ingress thread assigns sequence numbers from a plain counter and is the only writer to the store.

    BUYS Ordering with no atomics, locks or coordination.

    COSTS Ingest throughput is bounded by one thread, and the gateway is a single point of failure (see limits).

    Core/Ingress/NetworkGateway.inl

    Append first, then multicast once

    The message is written to the store before a single UDP datagram serves all replicas.

    BUYS Cost independent of replica count; nothing a replica misses is unrecoverable within the ring's horizon.

    COSTS UDP loses packets, so recovery logic is required, and history is bounded by the ring.

    NetworkGateway::pollSockets · SequenceStore

    Seqlock slots in a memory-mapped ring

    Each slot carries a version counter (odd = being written). The retransmit thread reads without ever blocking the writer.

    BUYS The ingress writer never waits for a reader.

    COSTS A reader may retry (4 attempts) and, if contended, report the record as too old. The file is mapped with MAP_POPULATE and locked with a best-effort mlock.

    Core/Ingress/SequenceStore.hpp

    Plain structs on internal channels

    Sequenced messages, heartbeats, retransmit requests and egress batches (a fixed header, then raw events) are plain structs sent as raw bytes — no serialization layer.

    BUYS No encode/decode work between gateway and replicas.

    COSTS Those channels assume identical struct layout and byte order on every host. Explicit encoding is left to the product's own wire protocol.

    SequencedInboundMessage · EgressBatchHeader

    Telemetry off the critical path

    The matching thread only writes timestamps into its own arena slot; a separate thread forwards finished traces over UDP.

    BUYS Measurement adds a few stores and clock reads to the hot path, not I/O.

    COSTS If the trace queue is full the trace is dropped (engine events are never dropped). Every timestamp is a clock_gettime call.

    SPSCProducerPolicy · TelemetryForwarder

    Two clocks

    rdtscp for timings that stay on one machine; CLOCK_TAI for anything that may be compared across machines. TAI has no leap seconds, so it can't step backwards the way CLOCK_REALTIME occasionally does.

    BUYS Cheap local timing, and cross-machine deltas that don't go negative.

    COSTS Cross-machine numbers are only as good as the clock sync. The documented setup is software PTP, which the repository's README puts at tens of microseconds — and marks as not yet verified end to end.

    Core/Telemetry.hpp · Tools/ptp/

    Opaque counters, not product fields

    Each trace reserves four 32-bit slots that Core carries and windows but never interprets. The product decides what slot 0 means.

    BUYS Core stays product-agnostic, and PerformanceServiceApp needs no per-product build. The slots fit inside padding the 64-byte record already had.

    COSTS Generic names (ExtCounter0…) in the output, a fixed count of four, and slot meanings documented on the product's side. The alternative — templating the trace on a product type — would have forced the aggregator to be built per product.

    OrderTrace · MetricKind::ExtCounter0…3

    Cache-line-sized records

    OrderTrace and each sequence-store slot are 64-byte aligned.

    BUYS One record per cache line; no false sharing between neighbours.

    COSTS A field change that crosses 64 bytes doubles the arena's footprint — the build fails on purpose when it happens (static_assert on OrderTrace).

    WHY NOT AERON

    Aeron is the established open-source transport for a design like this one, so the obvious question is why the networking here is hand-written. To find out, I built a second transport on Aeron 1.53.3 (its C media driver and C++ client) and ran both through the same benchmark. The benchmark uses the real gateway, a TCP client that sends at a fixed rate, and a consumer thread on each replica that checks it sees every command once and in order, and times it. The harness is in the repository's Benchmarks/ directory. The Aeron transport is an experiment. It is not part of Core.

    Why the hand-written transport stays

    • It was not slower. Over UDP, Aeron's median latency was 63 to 73 µs against 38 to 48 µs at 500,000 commands/s, and the two have the same ceiling here.
    • It does not replace the store. A late or lagging replica cannot catch up from an Aeron stream. Using Aeron would mean keeping the sequence store and retransmit server anyway, so there would be two recovery paths for one problem.
    • A custom flow control would only recreate half of it. Aeron lets you write one, and one could keep a slow replica from holding the sequencer back. That is the property the hand-written design already has. Catching up is a separate problem that flow control cannot solve. The plug-in would also run inside the media driver and depend on its internals.
    • It adds a process per host and a decision about spinning. The fast driver settings keep one to three cores busy even when idle.
    • Where Aeron would earn its place: links between processes on one host, where shared memory is far faster, and the Archive if replay needs to outlive the sequence store's ring.
    LIMITS OF THIS TEST One machine under WSL2, so tail latencies include hypervisor noise. The C driver, not the Java one. No core pinning, jumbo frames or kernel bypass, and the Aeron rig is not tuned beyond a few driver settings. Nothing here was run across two real hosts. A hybrid, with Aeron for live traffic and the sequence store for catch-up, was not built or measured. The result is for this design on this setup, not a general claim about Aeron.

    What limited the rate

    The measurement product's engine is not the limit: in the 100,000 and 500,000 orders/s runs after the rework its execution time was 75 to 85 ns at p50, and its p99 was at most 510 ns in any one-second window. Three things limited the rate or the stability, each found by changing one thing and rerunning.

    • Leadership under load (fixed by the egress rework). Before the rework the leader changed 47 to 84 times in every run from 100,000 to 500,000 orders/s, and 6 times at 70,000. It did not change at 60,000 and below. The cause was the leader's publisher, which sent each event as its own datagram. Above about 70,000 orders/s that many system calls could not keep up, so the event queue (16,384 slots) filled and the leader's matching thread blocked on it. The leader then fell about 20 ms (about 2,000 commands at this rate) behind the other replica. The arbiter did its job: it saw a lagging leader, promoted the follower and increased the epoch. The old leader caught up, and the cycle repeated about every quarter of a second. Four observations support this. The arbiter's own diagnostics showed every replica's heartbeat fresh (younger than 2.2 ms) while the lag moved from one replica to the other. With replica egress switched off the leader never changed. Widening the arbiter's windows to 100 and 200 ms did not stop it, because the lag was real. And after the rework the inbound queues, which had filled behind the blocked matching thread, no longer fill. Now a datagram carries every event that is waiting. At 100,000 orders/s the publisher sent 233,827 datagrams for 2,959,738 events (13 events each on average), and the leader changed in 1 run of 21.
    • Waking sleeping replicas. With blocking receivers the gateway ingests only about 320,000 to 347,000 orders/s. Five runs out of five with the reworked egress reached 326,000 to 342,000 at targets of 400,000 and 500,000. In the two runs I sampled (a 300,000 target and a 400,000 target) the gateway's ingress thread was at 90% and 93% of a core, the busiest thread in its process. In an earlier run of the old stack with egress off, it spent 91% of its time in the kernel. With receivers that spin for 100 µs the gateway ingests 500,000 orders/s (the optional spin window), in seven runs out of seven. The old stack with blocking receivers and egress on also reached 500,000. A likely reason is that the slow egress kept the replicas busy, so their receivers always found a datagram waiting and never had to be woken. I did not test that.
    • One egress thread. The gateway's egress thread (identified by thread start order) does the work for every event: it decodes, encodes, writes to the client, adds to the public feed and, by default, prints a line. With the console echo on, it used 34% of a core at 100,000 orders/s, 91% at 300,000 and 93% at 500,000. At 500,000 the gateway lost 21% of the events in the run that counted them (839,885 of 3.94 million). Of the nine echo-on runs at 400,000 and 500,000, eight lost events (4% to 25%). The one that lost none used the 100 µs receiver spin window at 400,000. I infer that the thread fell behind and the kernel dropped the datagrams that no longer fitted in its 4 MiB receive buffer, but I did not read the kernel's drop counter. With the echo off, the thread used about half a core at 500,000 orders/s (about 1 million events per second) and lost none in three runs out of three. The printed line is the expensive part. A product that runs at load switches it off.

    Run length. The runs above 100,000 orders/s are short on purpose. The measurement product keeps each order token in a fixed table. At commit c6e1212 (the 50,000 orders/s table) the table slowed to milliseconds per order after about 2.6 million orders, so that table uses only the windows before that point. From commit df58d8b it stops registering at 1,835,008 tokens (7/8 of 221) and rejects further new orders. This order mix registers a token for about 80% of its orders, so a run stays under the new limit up to about 2.3 million orders. I kept every run after the rework at or below 2.0 million. The limit belongs to that product, not to Core.

    KNOWN LIMITS

    Things a careful reader would find, stated up front.

    SINGLE GATEWAY The sequencer, sequence store, retransmit server, arbiter and egress gateway all live in one process. Matching is replicated; the front door is not.
    STORE IS A BUFFER The sequence store is file-backed but is zeroed every time the gateway starts, and the sequence restarts at 0. It works as a bounded retransmit buffer for live replicas, not as crash-recovery storage. A running replica that sees the sequence start over ignores those early commands (it logs a warning for each) rather than apply them again, so replicas must be restarted along with the gateway.
    EGRESS HAS NO GAP-FILL The replica → egress-gateway multicast has no retransmit path, so a lost egress datagram is not recovered. Only the leader publishes, so the events around a leadership change are also missing; the gateway counts them as it does any other gap.
    RESTART / LATE JOIN A fresh replica starts by expecting sequence 0 and catches up by retransmit, replaying the whole history in order. This is tested, including on a quiet exchange where no live message ever arrives. It works only while the newest sequence number is at most the ring capacity minus one (220 − 1 by default); one more message evicts sequence 0, and the replica stops itself.
    ELECTION MODEL Leadership is decided by a central arbiter with a fencing token, not by a consensus protocol among the replicas. The arbiter recomputes only when a heartbeat arrives.
    EGRESS GATEWAY CAPACITY One thread receives, encodes and delivers every event. With the console echo on, it ran at over 90% of a core from 300,000 orders/s, and in 8 of 9 runs at 400,000 and 500,000 the gateway lost events (4% to 25%). With the echo off it used about half a core at 500,000 orders/s and lost none. The gateway counts the events that never arrived, from the ordinals, and warns at most once a second, but it cannot recover them. Publishing from every replica would not fix this, because the extra copies would arrive at the same socket and thread.
    IDLE COST Three threads per replica spin at 100% whether or not any traffic arrives, so two replicas keep about six cores busy at idle. That is the price of the busy-polling design, and it is not tuned or pinned.
    TRACE ARENA The arena has 220 slots. A command that rests long enough for the ring to wrap loses its timing record; a collision counter makes that visible but can't prevent it.
    CLOCKS Cross-machine timing depends on clock sync that has not been exercised across two real hosts yet.
    SCOPE One engine per replica process. Every measurement on this page comes from one machine under WSL2, with every process on the same host.
